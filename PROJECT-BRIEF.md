# Project brief — Security Incident Tracker

## Purpose

Practice web programming by building a small interface for recording and reviewing fictional security incidents. The core project is a single-browser demonstration. Real users, confidential reports, and server-enforced permissions belong to the optional backend extension.

## Instructions

1. Sketch the dashboard, report form, and detail page before implementing them.
2. Write the field rules below in your own words and use them consistently in forms, data operations, and tests.
3. Build the smallest working flow first: create one fictional report and see it in a list.
4. Expand through the numbered lessons. Track evidence against the acceptance checks below.
5. Keep implementation work in a separate repository so this curriculum remains a code-free guide.

## Core pages and behavior

| Page | Required behavior |
| --- | --- |
| Dashboard | Show totals by status, list incidents, combine text/status/severity filters, show empty results |
| Report incident | Validate fields, retain invalid input, create one record, announce success |
| Incident detail | Show all report fields and allow demo status changes |
| Not found | Explain an unknown page or record and provide a recovery link |

All pages share clear navigation, readable styling, visible focus, and responsive layout. A reset action restores fictional sample data after confirmation. Label status controls as demo behavior until server permissions exist.

## Incident fields

These are course design choices, not an industry incident-management standard.

| Field | Rule |
| --- | --- |
| Identifier | Unique and stable; generated by the app in demo mode and by the server in the backend extension |
| Title | Required; 5–100 characters after trimming surrounding whitespace |
| Description | Required; 20–2,000 characters after trimming surrounding whitespace |
| Category | One of Phishing, Suspicious Login, Malware Alert, or Other |
| Severity | One of Low, Medium, or High; supplied by the reporter for this exercise |
| Status | Starts Open; can change to Investigating or Resolved; reopening to Open is allowed |
| Created time | Set at creation, stored consistently, and displayed in a readable local format |
| Updated time | Changes after a successful status change |

For this exercise, JavaScript string length determines the limits; note that emoji can occupy multiple string units. Check the same rules server-side in the optional extension. Search matches title or description, ignores case and surrounding search whitespace, and combines with both filters. Dashboard totals describe all incidents, while the result count describes filtered incidents.

## Fictional practice reports

Create at least five records of your own. Suggested scenarios include a simulated password-reset email, a training-account login alert, and an antivirus demonstration alert. Use invented names and no real credentials, email contents, attachments, or confidential incident details. Include two identical titles with different identifiers to test identity handling.

## Optional server permission matrix

| Operation | Anonymous | Reporter | Administrator |
| --- | --- | --- | --- |
| Read incidents | Denied | Own reports only | All reports |
| Create report | Denied | Allowed, owned by the current user | Allowed, owned by the current user |
| Change status | Denied | Denied | Allowed |
| Assign administrator role | Denied | Denied | Outside the public app; controlled setup only |

The server determines user identity and ownership. Hiding buttons is only a user-interface choice. Deleting reports, attachments, notifications, and public self-registration are outside the required scope.

## Core acceptance checklist

- [ ] A valid submission appears exactly once and updates the totals.
- [ ] Missing, whitespace-only, short, long, and unexpected values receive useful feedback.
- [ ] Search and both filters combine correctly; clearing them restores the list.
- [ ] Details, missing records, navigation, and status changes behave consistently.
- [ ] Refresh preserves fictional data; corrupted storage and reset are handled.
- [ ] The interface works with keyboard navigation, visible focus, narrow screens, and zoom.
- [ ] Meaningful tests include both success and failure cases and detect a deliberate regression.
- [ ] The production build succeeds and hosted direct links work.
- [ ] The README includes screenshots, setup instructions, testing evidence, and honest limitations.

## Optional backend acceptance checklist

- [ ] Invalid direct API requests fail even when browser validation is bypassed.
- [ ] Database records survive restart and transactional updates remain consistent.
- [ ] Reporter A cannot access Reporter B’s data through any read or write operation.
- [ ] Login, logout, expiry, role checks, CSRF protection, and rate limiting have recorded tests.
- [ ] No private secrets are in the frontend or repository; logs omit sensitive credentials and bodies.
